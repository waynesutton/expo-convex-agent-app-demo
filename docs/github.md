# Publish this template to GitHub

This guide takes you from a local folder to a GitHub repo that your team can clone and strangers can use as a template. It covers the first push, the template repo setting, the links you point back at your repo, and the settings worth turning on.

The upstream template is already published at [github.com/waynesutton/expo-convex-agent-app-demo](https://github.com/waynesutton/expo-convex-agent-app-demo). Use that as a template or fork it, then follow the steps below on your copy.

## Before you start

You need three things:

1. A GitHub account. Free is fine, public and private repos both work.
2. Git installed. Check with `git --version`. Any version from the last few years works.
3. A way to authenticate. Pick one:

| Method | Setup | Best for |
|---|---|---|
| GitHub CLI (`gh`) | `brew install gh` then `gh auth login` | Fastest path, handles auth and repo creation in one tool |
| SSH keys | [GitHub SSH docs](https://docs.github.com/en/authentication/connecting-to-github-with-ssh) | Long term daily use |
| HTTPS + token | Create a personal access token in GitHub settings | Machines where you cannot install extra tools |

The CLI path is used throughout this guide. Every step has a github.com fallback.

Set your identity if this machine has never used git:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

## Check what will be committed

Do this before the first commit, not after. The `.gitignore` at the repo root keeps the right things out:

| Ignored | Why |
|---|---|
| `.env.local`, `.env*.local` | Deployment URLs and deploy keys stay local |
| `packages/backend/convex/_generated/` | Regenerated by `npx convex dev` on every machine |
| `node_modules/`, `.expo/`, `dist/` | Installed and built artifacts |
| `apps/native/ios/`, `apps/native/android/` | Prebuild output, EAS builds from source |
| `*.log`, `.DS_Store` | Noise |

Nothing secret ships. A fresh clone rebuilds all of it.

Two spot checks worth 30 seconds:

```bash
# Preview exactly what git will track. Read the list, look for anything odd.
git init
git add --dry-run . | head -50

# Grep the tree for key material before it enters history.
grep -rn "sk-ant\|sk-proj\|fc-" --include="*.ts" --include="*.tsx" --include="*.json" . \
  --exclude-dir=node_modules || echo "clean"
```

If a key shows up, remove it and put it where it belongs: LLM keys go on the device through the settings screen, tool keys go in Convex env vars (`npx convex env set`). See `docs/byok.md`.

## Initialize and commit

```bash
cd /path/to/expo-demo
git init
git add .
git commit -m "feat: expo-demo template, expo plus convex agent chat"
```

Git defaults to a branch named `main` on recent versions. If yours says `master`:

```bash
git branch -M main
```

One commit is enough. Template users start from a clean history anyway, so there is no need to split the initial import into pieces.

## Create the repo and push

### With the GitHub CLI

One command creates the repo, wires the remote, and pushes:

```bash
gh repo create expo-demo --public --source . --push
```

Swap `--public` for `--private` to keep it to yourself or your org. To create under an org instead of your account:

```bash
gh repo create your-org/expo-demo --public --source . --push
```

### On github.com

1. Go to [github.com/new](https://github.com/new).
2. Name it `expo-demo` or whatever your fork is called.
3. Leave every initializer unchecked. No README, no license, no gitignore. All three exist here and initializers create a conflicting first commit.
4. Create the repo, then wire it up locally:

```bash
git remote add origin git@github.com:<you>/expo-demo.git
git branch -M main
git push -u origin main
```

Using HTTPS instead of SSH? The remote URL is `https://github.com/<you>/expo-demo.git` and git prompts for your token on push.

Verify it landed:

```bash
git remote -v
gh repo view --web   # opens the repo in your browser
```

## Mark it as a template repo

A template repo gives visitors a green "Use this template" button. They get a copy with a clean single commit history instead of a fork chained to yours. For a starter kit this is what you want: forks are for people who plan to pull your future changes, templates are for people building their own thing.

With the CLI:

```bash
gh repo edit <you>/expo-demo --template
```

On github.com: repo Settings, General, check "Template repository" near the top.

Both paths still allow forking. You are adding an option, not removing one.

## Point the app and landing page at your repo

Three files reference the repo URL. Set them after the repo exists, commit, and push again.

1. `apps/native/lib/links.ts`. Set `REPO_URL` to your repo URL. The in app About screen then links to your README, the fork guide, and your docs folder. Empty string hides those rows instead of showing dead links.

```typescript
export const REPO_URL = "https://github.com/<you>/expo-demo";
```

2. `landing/index.html`. Set the `REPO_URL` constant at the top of the script tag. This unhides the GitHub and Fork it links on the landing page.

3. `landing/docs.html`. Same constant, same place.

```bash
git add apps/native/lib/links.ts landing/
git commit -m "chore: point REPO_URL at the published repo"
git push
```

## Recommended repo settings

None of these block anything. All of them help people find and trust the repo.

- **Description.** "Mobile agent chat template. Expo front, Convex back, BYOK keys stay on device." Set it in the About box on the repo page or with `gh repo edit --description "..."`.
- **Topics.** `expo`, `convex`, `react-native`, `ai-agent`, `template`. Topics are how template hunters search GitHub. Set them in the About box or with `gh repo edit --add-topic expo --add-topic convex`.
- **Issues on, wiki off.** The docs live in `docs/` and ship with every clone. A wiki splits them from the code.
- **Social preview image.** Settings, General, Social preview. A screenshot of the app or the landing page makes shared links look intentional.
- **Branch protection on `main`.** Skip it solo. The moment a second person has push access, require a pull request before merging: Settings, Branches, add a ruleset for `main`.
- **Releases.** Optional. Tag a `v1.0.0` when the template is stable so template users can see what changed since they copied it: `git tag v1.0.0 && git push --tags`.

## What a fresh clone needs

Someone who clicks "Use this template" or clones the repo runs:

```bash
npm install
cd packages/backend && npx convex dev     # login, project created, URL printed
cd ../../apps/native
cp .env.example .env.local                # paste the printed URL
npx expo start
```

Or they open the repo in a coding agent and paste `docs/one-prompt-setup.md`. Agents that run unattended use `CONVEX_AGENT_MODE=anonymous npx convex dev` and skip login entirely. See the agent section in `docs/setup.md`.

Each clone provisions its own Convex project. Your deployment, env vars, and data never touch theirs.

## What not to commit, ever

- `apps/native/.env.local` and `packages/backend/.env.local`
- Any real API key, in any file, in any commit
- `convex/_generated/`. Committing it causes type drift between machines.

If a key slips into history, deleting the file in a new commit does not remove it. The old commit still holds it. Recovery order matters:

1. Rotate the key at the provider first. Treat it as burned the moment it was pushed.
2. Rewrite history with [`git filter-repo`](https://github.com/newren/git-filter-repo) or the [BFG Repo-Cleaner](https://rtyley.github.io/bfg-repo-cleaner/), then force push.
3. GitHub secret scanning emails you about known key formats on public repos. Read those emails.

## Troubleshooting

**`remote origin already exists`.** You ran `git remote add` twice or `gh repo create` already wired it. Check with `git remote -v`, fix with `git remote set-url origin <url>`.

**Push rejected, authentication failed.** On HTTPS, GitHub wants a personal access token, not your account password. On SSH, run `ssh -T git@github.com` to test the key. Or sidestep both with `gh auth login`.

**Push rejected, `fetch first`.** The GitHub repo has a commit yours does not, usually from checking an initializer box at creation. Fix: `git pull --rebase origin main` then push, or delete the remote repo and recreate it empty.

**Everything pushed but the repo looks huge.** Check for a committed `node_modules` or `dist` with `git ls-files | grep node_modules`. If found, `git rm -r --cached node_modules`, commit, push. The `.gitignore` prevents this on a clean start, so this usually means files were added before the ignore file existed.

**"Use this template" button missing.** The template checkbox is per repo, not per account. Revisit Settings, General, "Template repository."
